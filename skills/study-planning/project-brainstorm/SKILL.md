# 项目头脑风暴 / Project Brainstorm

在动手之前，把一个项目想法从"听起来不错"推到"明天上午可以做第一件事"。

这个 skill 存在的理由是：**学生卡住的不是没有想法，是没法判断哪个想法真做得动。**
"做个环保相关的项目"这句话里，缺可行性、缺代价、缺"做完之后手里有什么"。
把这些摆出来，他自己就能选。

## 何时使用 / When to use

- 学生想做点什么但方向模糊（"想做个项目""想搞个社团"）
- 他有一个具体想法，想知道值不值得投入
- 已有项目做不下去了，要判断是转向还是收尾
- 要选研究课题、竞赛选题、EE/IA 题目

**不适用于** / Not for：

- 项目已经定了，要排时间 —— 那是 `deadline-to-study-plan`
- 整理已经做完的经历 —— 那是 `activity-profile-builder`
- 问"招生官会怎么看我现有的背景" —— 那是 `admissions-reader`
- 深挖某段经历对他的意义 —— 那是 `reflection-interviewer`

## 流程 / Process

### 1. 读三样，一次读齐

| 读什么 | 用来判断 |
|---|---|
| `get_profile` | 年级与课程体系——**决定还剩多少时间**。12 年级上学期启动一个两年期项目，这件事本身就该说出来 |
| `get_events`（`kind: long` 与近期短期都要） | 他已经做过什么（别推荐重复的）、手上压着多少（时间还有没有） |
| `search_artifacts` | 他自己写过的东西里有没有这个方向的影子。**真正的好项目多半藏在他已经在意的事里**，不在"什么背景提升项目热门"里 |

### 2. 去重，再数还剩几件事

把上一步搜到的资料条目一起丢给 `dedupe_findings`。

**这一步不能省。** 学生的反思、复盘、活动记录里同一件事会出现好几遍——
一段机器人社的经历可能有一条长期事项、两篇反思、一次周复盘提到。
不去重就会得出"他在这个方向上已经积累很厚"的错误结论，然后劝他别做。

**去重分两半，工具只做前一半：**

| | 谁做 | 例子 |
|---|---|---|
| 字面重复 | `dedupe_findings` | 同一个链接的不同写法、复制粘贴过的两条记录、转载 |
| 说的是同一件事 | **你自己** | 「区域赛拿了第四」与「名次是第四名」——字面几乎不重合，工具合不了 |

所以拿到 `kept` 之后**再自己过一遍标题和片段**，把讲同一件事的并掉，然后才报数字。
返回里的 `similar` 只是"差一点就算重复"的字面接近，不是语义相关，也不代表已经合并。

如实说出两个数：「原始 8 条，去掉重复后是 3 件事」。**不要把重复计数当成积累厚度**——
这是这个流程最容易犯的错，代价是劝退一个其实还很空的方向。

### 3. 直接给三个方案

**不要先问"你想做哪个领域"。** 拿着第 1 步读到的东西，直接给三个具体方案。
每个方案必须写满这五项，缺一项就是没想清楚：

```markdown
### 方案 <N>：<一句话说清楚做什么>
- **第一件事**：明天/这周能动手的那一件，具体到动作
- **要什么**：时间（每周几小时 × 几个月）、钱、人、设备、许可
- **做完手里有什么**：一份报告 / 一个能跑的东西 / 一场办成的活动 / 一组数据
- **可能死在哪**：最可能让它半途而废的那一个原因，写具体
- **和你已有的关系**：接着 <某段经历> 往下走 / 是个全新方向（两者都行，说清楚就好）
```

三个方案要**在代价上拉开差距**——一个轻的（几周）、一个中的（一学期）、一个重的（一年以上）。
三个都是"一学期的中等项目"等于只给了一个。

**「可能死在哪」是这五项里最有用的一项。** 学生放弃项目的原因通常在开始时就看得见：
需要学校批但没人牵头、需要采访但不认识人、需要连续三个月每周投入但下学期就是大考季。
说出来，比列十个优点有用。

### 4. 只问真正的岔路口

三个方案摆完，用 `ask_user` 一次问完剩下的选择（最多 4 问）。值得占一问的：

| 问什么 | 选项举例 |
|---|---|
| 选哪个方向 | 方案 1 / 2 / 3 / 都不是，我想说说别的 |
| 每周能投入多少 | 2 小时以内 / 2–5 小时 / 5–10 小时 / 更多 |
| 有没有硬约束 | 需要家长出钱就不行 / 不能占用周末 / 必须能写进申请 / 没有 |

**不要问"你对什么感兴趣"。** 这问题他答不好，而且第 1 步读到的东西比他临时想出来的答案准。

### 5. 定下来就落地

- `propose_events` 提案一条 `kind: long` 的长期事项（这个项目本身），
  加**前三个里程碑**的短期事项。只提前三个——再往后排的都是猜的。
  每个里程碑都要有交付物，"推进项目"不是交付物。
- `propose_artifact` 存一份 `kind: plan` 的构思稿，把三个方案、选了哪个、
  为什么选、当时判断的风险都写进去。**没选的那两个也要留着**——
  半年后项目卡住时，这份记录是最有用的东西。

赶某个比赛或申报截止日的，用 `resolve_deadline` 换算，别口算。

## 输出格式 / Output

```markdown
## 你现在的位置
<年级 / 体系 / 手上压着什么 / 还剩多少可支配时间>

## 相关的积累
去重后 <N> 件（原始 <M> 条，合并了 <M-N> 条重复）：
- <一件事> —— 来自 <哪几条记录>

## 三个方案
<按上面那个模板，三段>

## 我的看法
<一段。可以有倾向，但要说清楚倾向的依据，并且明确这是他的决定>
```

## 边界 / Boundaries

- **不吹可行性**：三个方案里如果有一个你觉得多半做不成，就写在「可能死在哪」里，
  不要为了凑三个而端上来一个漂亮的空壳。
- **不替他选**：可以有倾向、要给依据，但选择是他的。他的时间、他的兴趣、他要承担后果。
- **不为了申请而编项目**：不说"这个方向招生官会喜欢"。没人知道，说了就是编。
  一个他自己不在乎的项目做不完，做完了也写不出真东西。
- **不编数据支撑可行性**：不引用"这类项目通常需要 X 小时"、"同类竞赛录取率"这种
  你没有来源的数字。要么说清楚是估算及估算依据，要么不说。
- **去重结果如实说**：合并了几条就说几条。把重复计数当成积累厚度是这个流程最容易犯的错。
- **不推荐需要造假才能完成的项目**：需要伪造数据、冒用身份、绕过学校规定的，直接说不做。
- **不承诺结果**：项目做不做得成取决于他，不是取决于这份规划。

## Token 控制 / Token discipline

- 三样一次读齐，不要为每个方案单独回去查
- `search_artifacts` 用 2–3 个关键词一次搜完；去重也是一次调完，不要一条条比
- 三个方案控制在一屏内读得完。每项一两句，写不下说明还没想清楚
- 没被选中的方案不要在后续轮次里反复重贴，构思稿里存过就够了
