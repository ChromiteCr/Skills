# 做一个自己的技能 / Skill Creator

把学生反复用到的一套做法，问成一份能真正跑起来的 `SKILL.md`。

技能不是"给 AI 的一段说明"，是**一份可执行的规格**：它决定 agent 在什么时候被唤起、
能碰哪些数据、按什么步骤走、哪些事不许做。所以这个 skill 的重点不在把 markdown 写漂亮，
在于把三件事问清楚：**什么时候用它、它要读什么、它绝对不做什么。**

## 何时使用 / When to use

- 学生发现自己反复在交代同一套要求（"每次都要提醒你先看我的课表"）
- 他有一套自己的方法想固定下来（错题整理的流程、面试准备的清单）
- 他想改自己之前做的某个技能

**不适用于** / Not for：

- 只是想让 AI 这一次按某种方式回答 —— 直接说就行，不必做成技能
- 想要的能力运行时根本没有（比如收发邮件）—— 技能只能调用已有能力，
  做不出新能力。这种情况如实说，别写一个跑不起来的壳

## 需要的输入 / Inputs

| 输入 | 必填 | 说明 |
|---|---|---|
| 运行时有哪些能力 | 是 | **动笔之前先调 `list_capabilities`**。能力名是运行时定的，凭印象写必错 |
| 学生想固定的那套做法 | 是 | 全部内容来自这里 |
| 参考用的现有技能 | 否 | 学生说"我想要个类似 X 的"，可以用 `read_skill` 读 X 看它怎么写的 |

## 流程 / Process

**先查能力，再问需求，最后才写。** 顺序反了会写出一份声明了不存在能力的技能。

1. **查能力**：调 `list_capabilities`，记住有哪些读能力、哪些提案能力。

2. **问"什么时候用它"**——这是最重要的一问，因为 `description` 决定 agent 会不会在
   正确的时刻想起这个技能。追到具体的**触发场景**，不要停留在"帮我学习"：
   > 「你希望什么时候它自动派上用场？给我两三句你会说的原话。」

   拿到的原话直接写进 `description`，那正是 agent 用来判断的依据。

3. **问"它要做什么"**：让他按顺序讲一遍这套做法。答得笼统就追一层——
   "先看看我的情况"要问成"具体看什么：课表？成绩？还是之前写过的东西？"
   每问出一个"看什么"，对照第 1 步的能力清单确认有没有对应的能力。

4. **问"它绝对不做什么"**：**这一问不能省。**
   好技能和坏技能的差别多半在边界上，而学生一开始想不到要写边界。
   给他几个方向挑：不代写哪些内容、不编造什么、不替他做哪些决定、什么时候该说"我不知道"。

5. **定能力与轮数**：
   - 只读的流程就**别声明 capabilities**——不写就是只读，这是最安全的默认值
   - 要写库才声明，且只声明真正用到的。多声明不会更强，只会让用户看到不必要的授权
   - `outputs` 要和 capabilities 对上：写了 `document` 就得有 `propose_artifact`
   - 一问一答的访谈类流程 `max_rounds` 给到 50 以上，很吃轮数

6. **写出来**：按下面的骨架写完整一份，调 `propose_skill` 出确认卡。
   卡片上会显示解析结果与授权范围，解析不过会把错误列出来——**照着错误改，再提一次**。

## 输出格式 / Output

访谈阶段是正常对话。**一次只问一件事**——一口气抛出五个问题，
学生会挑最好答的两个回答，剩下的就永远缺着，而缺的多半正是边界。

要出卡之前先把要点复述一遍确认：

```markdown
我理解你要的是这样一个技能：

**什么时候用**：<触发场景>
**它会读**：<能力清单>（<读还是提案>）
**流程**：<三到五步>
**绝对不做**：<边界>

对的话我就写出来。
```

## 边界 / Boundaries

- **不编造能力名**：`capabilities` 里的每一个都必须来自 `list_capabilities` 的返回。
  拿不准就再查一次。写错了那个技能装上去就是坏的。
- **不替学生想需求**：他说不清要做什么，就继续问，不要按"学生一般会想要 X"补齐一份。
  写出来的是他不会用的东西。
- **不省略边界那一问**：没有边界的技能等于没有约束的 agent。
- **不夸大**：技能只能调用已有能力。学生要的做不到就直说，不要写一份看起来能跑、
  实际调不到工具的规格。
- **不代替确认**：写完必须走 `propose_skill` 出卡，由学生自己看过授权范围再存。
- **写自己的边界也要老实**：如果生成的技能会写库，在复述时明确告诉他"这个技能能改你的数据"。

## Token 控制 / Token discipline

- `list_capabilities` 一次调完，不要每写一个字段查一次
- 访谈每轮只问一件事，输出很短
- 只有最后 `propose_skill` 那一次输出完整 SKILL.md，中途不要反复贴草稿
