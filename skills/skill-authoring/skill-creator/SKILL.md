# 做一个自己的技能 / Skill Creator

把学生反复用到的一套做法，变成一份能真正跑起来的 `SKILL.md`。

技能不是"给 AI 的一段说明"，是**一份可执行的规格**：它决定 agent 在什么时候被唤起、
能碰哪些数据、按什么步骤走、哪些事不许做。

**做法是先写出来给他改，不是先问一轮再动笔。**
学生说不清"我想要什么样的技能"，但看着一份具体的草稿，
他能立刻指出"这里不对，我要的是……"。写一版的成本很低，问八轮的成本很高。

## 何时使用 / When to use

- 学生发现自己反复在交代同一套要求（"每次都要提醒你先看我的课表"）
- 他有一套自己的方法想固定下来（错题整理的流程、面试准备的清单）
- 他想改自己之前做的某个技能

**不适用于** / Not for：

- 只是想让 AI 这一次按某种方式回答 —— 直接说就行，不必做成技能
- 想要的能力运行时根本没有（比如收发邮件）—— 技能只能调用已有能力，
  做不出新能力。这种情况如实说，别写一个跑不起来的壳

## 需要的输入 / Inputs

| 输入 | 必填 | 说明 |
|---|---|---|
| 运行时有哪些能力 | 是 | **动笔之前先调 `list_capabilities`**。能力名是运行时定的，凭印象写必错 |
| 学生想固定的那套做法 | 是 | 一句话就够，剩下的靠草稿去逼出来 |
| 参考用的现有技能 | 否 | 学生说"我想要个类似 X 的"，可以用 `read_skill` 读 X 看它怎么写的 |

## 流程 / Process

**先查能力，再写草稿，最后一次问完。** 顺序反了会写出一份声明了不存在能力的技能。

1. **查能力**：调 `list_capabilities`，记住有哪些读能力、哪些提案能力、哪些提问能力。

2. **直接写出第一版**：按学生那句话，用下面的骨架写一份**完整**的 SKILL.md 贴给他看。
   拿不准的地方按最保守的选项定并标出来：
   - 拿不准要不要写库 → **不声明 capabilities**（缺省即只读，最安全）
   - 拿不准触发场景 → 按他那句话的措辞写 `description`，标注"这句最关键，下面问你"
   - 拿不准边界 → 先写三条通用的（不代写、不编造、不替他做决定），标注待确认

   不要贴一个填空模板让他填。**贴一份能跑的完整草稿。**

3. **同一轮把关键分歧一次问完**：调 `ask_user`，最多 4 问。值得问的只有这几类：

   | 问什么 | 为什么值得占一问 | 选项举例 |
   |---|---|---|
   | 什么时候该自动派上用场 | `description` 是 agent 判断触发的唯一依据，写空了这技能永远不会被想起来 | 我主动说要用才用 / 每周固定时候 / 遇到某类情况时 / 其他 |
   | 要不要能改你的数据 | 决定 capabilities 的形状，也决定用户看到多大的授权面 | 只看不改 / 可以帮我加事项 / 可以帮我存文档 |
   | 绝对不许做什么 | **好技能与坏技能的差别多半在边界上**，而作者一开始想不到写边界 | 不替我做决定 / 不编造我没说过的 / 不代写文书 / 都要 |

   **不要问"这样可以吗"、"要不要我写出来"。** 草稿已经在他眼前了。

4. **按答案改定**：调整 `description`、`capabilities`、边界那一节。
   - 只读的流程就**别声明 capabilities**——不写就是只读，这是最安全的默认值
   - 要写库才声明，且只声明真正用到的。多声明不会更强，只会让用户看到不必要的授权
   - `outputs` 要和 capabilities 对上：写了 `document` 就得有 `propose_artifact`
   - 一问一答的访谈类流程 `max_rounds` 给到 50 以上，很吃轮数
   - 这个技能自己要不要问用户？要就声明 `ask_user`，并在正文里写清楚"先做出东西再问"

5. **出卡**：调 `propose_skill`。卡片上会显示解析结果与授权范围，
   解析不过会把错误列出来——**照着错误改，再提一次**。
   不要在出卡前再问一遍"确认要保存吗"，卡片本身就是那次确认。

category: <大类，如 study-planning>
version: 0.1.0

display_name: <中文名，界面上显示的>

  - <来自 list_capabilities>
outputs:
  - <chat / document / canvas / event>

suggest_hint: <一句话，运行时主动建议时说的>
---

# <中文名 / English name>

<一两句话说清楚它做什么。>

## 何时使用
- <具体场景>

**不适用于**：
- <边界外的场景，指向别的技能>

## 需要的输入
| 输入 | 必填 | 说明 |

## 流程

## 输出格式 / Output

第一版草稿（与问题卡同一轮发出）：

````markdown
先按你说的写了一版，你看着改：

```markdown
<完整的 SKILL.md 原文>
```

**我拿不准的：**
- <标注 1，下面问你>
- <标注 2>
````

## 边界 / Boundaries

- **不编造能力名**：`capabilities` 里的每一个都必须来自 `list_capabilities` 的返回。
  拿不准就再查一次。写错了那个技能装上去就是坏的。
- **不替学生想需求**：草稿是让他改的靶子，不是替他决定。
  每一处你自己拿的主意都要**标出来**，别混在正文里假装是他的意思。
- **不省略边界那一问**：没有边界的技能等于没有约束的 agent。
- **不夸大**：技能只能调用已有能力。学生要的做不到就直说，不要写一份看起来能跑、
  实际调不到工具的规格。
- **不代替确认**：写完必须走 `propose_skill` 出卡，由学生自己看过授权范围再存。
- **写自己的边界也要老实**：如果生成的技能会写库，在草稿里明确告诉他"这个技能能改你的数据"。

## Token 控制 / Token discipline

- `list_capabilities` 一次调完，不要每写一个字段查一次
- 草稿只贴完整的这一次，改定后也只贴改动的那几行 + 最后 `propose_skill` 那一份
- 问题一次问完。运行时对连续追问有硬上限，一次一问会在写完之前就把额度用光
