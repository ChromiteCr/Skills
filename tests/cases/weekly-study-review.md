# weekly-study-review

## Case 1: 正常复盘，有完成也有拖延

**输入 / Input**

本周事项（含已完成）：
- 08-01 物理错题整理（done）
- 08-02 英语阅读 3 篇（done）
- 08-03 数学真题一套（pending，已逾期）
- 08-04 化学笔记补齐（pending）

上一次复盘：一周前，当时写的调整动作是「把数学真题挪到早上做」。

用户提问：帮我复盘一下这周。

**期望 / Expected**

- [ ] 读事项时带了 `includeDone`，能看到完成的部分而不只是欠账
- [ ] **对账段落先写出来**（计划 4 件完成 2 件、数学真题拖了 1 天），只陈述不评价，不先问再写
- [ ] 归因用 `ask_user`，两件未完成的**一次问完**且各带具体选项（没时间 / 不知从哪下手 / 被挤掉 / 做了没标记）
- [ ] 把原因归到「计划 / 执行 / 外部」三类之一
- [ ] 检查了上次说要改的那条（挪到早上）这周有没有做到
- [ ] 「下周改什么」最多两条，且写清楚跟这周做法的区别
- [ ] 产出 `kind: review` 的 artifact，并对下周的调整动作出 `propose_events`

**反例 / Must not**

- 不得替学生编造未完成的原因（他跳过那一问就写「原因未明」，不从选项里挑一个替他填）
- 不得出现「你太拖延了」或「你已经很棒了」这类评价
- 不得给出三条以上的下周调整动作
- 不得一轮问一件原因，分两次占掉提问额度
- 不得在问原因之前什么都不产出

## Case 2: 这一周执行得很好

**输入 / Input**

本周计划 5 件，5 件全部 done，没有逾期。

用户提问：复盘一下。

**期望 / Expected**

- [ ] 如实说这周没什么要调的，按原样继续
- [ ] 仍然存一份复盘记录（数据本身有价值）
- [ ] 可以问一句这周为什么顺利（哪些做法值得保留），但不强求

**反例 / Must not**

- 不得为了让复盘显得有价值而硬找问题
- 不得因为没问题就输出一段空泛的鼓励充数

## Case 3: 数据缺失（本周几乎没有记录事项）

**输入 / Input**

本周事项：只有 1 条，且是别的 skill 自动生成的申请截止日。
学生自述「这周挺忙的但不知道忙了啥」。

**期望 / Expected**

- [ ] 明确说出系统里几乎没有本周记录，复盘缺少事实基础
- [ ] 把复盘转向「先建立记录」，而不是基于空数据编一段总结
- [ ] 可以引导学生口述这周做了什么，但记录时注明这些来自自述而非事项数据

**反例 / Must not**

- 不得在没有数据的情况下给出「计划 N 件完成 M 件」的对账
- 不得按「典型高中生的一周」补一个虚构的复盘
