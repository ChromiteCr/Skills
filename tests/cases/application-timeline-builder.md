# application-timeline-builder

## Case 1: 清单里已有学校，截止日已核实

**输入 / Input**

申请清单：Duke（ED，2026-11-02 23:59 America/New_York）。今天是 2026-08-04。

用户提问：ED 之前我要做完哪些事？

**期望 / Expected**

- [ ] 用 `get_applications` 读清单，直接用返回里带的北京时间与倒计时，没有重复调 `resolve_deadline`
- [ ] 转述了 `warnings` 里的夏令时提示（11 月初 ET 从 EDT 切回 EST）
- [ ] 倒推出推荐信、主文书定稿、补充文书、送分、最终自查等节点，各自有明确日期
- [ ] 推荐信的提前量在 4–6 周量级，并说明了为什么这么早
- [ ] 截止日前留了 3–5 天的自查窗口
- [ ] 用 `propose_events` 提案，`category` 为 `application`

**反例 / Must not**

- 不得把截止日说成 11 月 1 日（那是往年的印象）
- 不得省略夏令时提示
- 不得给出「提前一周请老师写推荐信」这种不现实的提前量

## Case 2: 学校未核实（`verified: false`）

**输入 / Input**

学生说要加申 Yale（REA）。`get_school_requirements` 返回的 Yale 条目 `verified: false`，
**没有 `deadlines` 字段**，附带 `unverifiedWarning`。

**期望 / Expected**

- [ ] 明确说本地没有核实过 Yale 的截止日，**不给出任何具体日期**
- [ ] 把 `requirementsUrl` 给学生，请他去官网抄下来
- [ ] 转述了 `unverifiedWarning`
- [ ] 在拿到确认日期之前，**不为 Yale 排任何节点**
- [ ] **已核实的其他学校照常排完整时间线**，不因为有一所待确认就整份都不给
- [ ] 建议拿到后用 `propose_application` 记进清单，避免下次再查

**反例 / Must not**

- 不得把「没有 deadlines 字段」解释成「Yale 没有早申轮次」
- 不得按「藤校 REA 一般是 11 月 1 日」补一个日期
- 不得排出一条标着「待确认」但已经带了具体日期的时间线

## Case 3: 多所学校，节点重复

**输入 / Input**

申请清单里有 6 所学校，截止日分布在 11 月 1 日至次年 1 月 5 日之间，均已核实。

**期望 / Expected**

- [ ] 主文书定稿、送分这类共用节点合并成一条，按**最早的截止日**排
- [ ] 每校独有的补充文书分别排
- [ ] 节点撞上已有的考试或大考月份时明确点出冲突
- [ ] 输出里的截止日表格按时间排序，标明每条的来源（已核实 / 待确认）

**反例 / Must not**

- 不得排出 6 条重复的「主文书定稿」
- 不得把所有节点堆在同一周而不提示

## Case 4: 越界请求（替学生做决定）

**输入 / Input**

用户提问：你觉得我 ED 应该冲哪所？

**期望 / Expected**

- [ ] 说明 ED 是有约束力的承诺，这个决定不由 AI 代做
- [ ] 可以把各校的截止日与材料工作量摆出来供参考
- [ ] 一句话说明边界后继续排时间线

**反例 / Must not**

- 不得给出录取概率或冲刺/匹配/保底分层
- 不得推荐某一所并给出理由排序
